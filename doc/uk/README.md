Локальне керування світильниками для басейну **MiBoxer PW01 / PW02** (LoRa, 433 МГц) через шлюз **MiBoxer WL-433** — без хмари, без голосового асистента, безпосередньо у вашій локальній мережі.

Виробник: [MiBoxer (Futlight Optoelectronics)](https://miboxer.com/) — [WL-433](https://miboxer.com/product/lora-433mhz-gateway), [PW01](https://miboxer.com/product/27w-rgbcct-par56-led-pool-light-lora-433mhz)

## Принцип роботи

Усередині WL-433 є модуль Wi-Fi Tuya. У локальній мережі шлюз є **одним** пристроєм Tuya: усі прив'язані лампи керуються через цей пристрій, а шлюз передає команди лампам через LoRa (433 МГц). Адаптер напряму спілкується зі шлюзом за **протоколом Tuya LAN 3.3** (TCP-порт 6668, шифрування AES локальним ключем) на основі перевіреної бібліотеки [tuyapi](https://github.com/codetheweb/tuyapi) (її також використовує ioBroker.tuya). Підтримуються й версії протоколу 3.1, 3.4 та 3.5 на випадок, якщо оновлення прошивки її змінить.

Лампи, зони та сцени керуються власними командами шлюзу в специфічній для виробника **точці даних 101** — тими самими командами, що надсилає застосунок MiBoxer. Шлюз повідомляє свій стан так само; крім того, адаптер запитує його під час підключення та під час кожного оновлення стану.

```text
ioBroker ──LAN: Tuya 3.3, TCP 6668──► WL-433 ──LoRa 433 MHz──► PW01 / PW02
```

**Посібник**, у якому кожен крок пояснено для початківців (встановлення, налаштування, зони, приклади, усунення несправностей): [English](../Manual_miboxer-wl433.md) ([PDF](../Manual_miboxer-wl433.pdf)) · [Deutsch](../Handbuch_miboxer-wl433.md) ([PDF](../Handbuch_miboxer-wl433.pdf)).

Вихідне дослідження (аналіз протоколу, джерела, план перевірки, розшифрована точка даних 101), німецькою: [Miboxer_WL-433_PW01_Protokollanalyse_lokale_Steuerung.md](../Miboxer_WL-433_PW01_Protokollanalyse_lokale_Steuerung.md) ([PDF](../Miboxer_WL-433_PW01_Protokollanalyse_lokale_Steuerung.pdf)). Інструкція з прив'язування ламп до шлюзу: [Anleitung_PW01_mit_WL-433_verbinden.pdf](../Anleitung_PW01_mit_WL-433_verbinden.pdf).

## Вимоги

1. Шлюз налаштовано в застосунку MiBoxer, і лампи до нього прив'язано.
2. **ID пристрою та локальний ключ** шлюзу. Виробник не підтримує платформу розробників Tuya для WL-433, але застосунок MiBoxer записує обидва значення у свій журнал налагодження: на Android читайте журнал переглядачем logcat, наприклад *LogFox*, поки застосунок запускається та керує шлюзом. **Локальний ключ змінюється під час кожного повторного сполучення шлюзу** — тоді його треба знову прочитати й ввести. Покрокова інструкція для початківців (німецькою, для Android, iPhone та iPad): [Anleitung_Geraete-ID_und_Local-Key_auslesen.md](../Anleitung_Geraete-ID_und_Local-Key_auslesen.md) ([PDF](../Anleitung_Geraete-ID_und_Local-Key_auslesen.pdf)).
3. Шлюз доступний з ioBroker (та сама мережа). Рекомендовано резервування DHCP; без указаної IP-адреси адаптер знаходить шлюз за його широкомовними UDP-повідомленнями (порти 6666/6667).
4. **Пристрої Tuya зазвичай приймають лише одне локальне підключення.** У тесті застосунок MiBoxer і адаптер були підключені одночасно; але якщо підключення знову й знову не вдається, закрийте застосунок на телефонах у тій самій мережі й не керуйте шлюзом одночасно іншими локальними інтеграціями (ioBroker.tuya, Home Assistant, tinytuya).

## Зони

Шлюз керує до 8 зонами (як пульт FUT086). Кожна команда може йти до однієї зони або до всіх зон, але шлюз повідомляє **лише один стан для всіх ламп: останнє налаштування, незалежно від того, до якої зони його надіслано**. Застосунок MiBoxer теж не показує окремий стан для кожної зони. Параметр *Керування зонами* пропонує два варіанти:

| Варіант | Стани | Підходить для |
| --- | --- | --- |
| **Вибір зони (типово)** | `light.*` показує стан шлюзу. `light.zone` (0 = усі зони, 1–8) визначає, до якої зони надсилаються команди `light.*`. | Більшість користувачів: кожен стан показує те, що повідомляє шлюз |
| **Окремий канал для кожної зони** | `light.*` показує стан шлюзу й надсилає команди до всіх зон. Крім того, `zones.zone1` … `zones.zone8` керують кожною зоною окремо. Канал зони показує останні значення, надіслані до цієї зони та підтверджені шлюзом; він залишається порожнім, доки до зони нічого не надіслано. | Скрипти та візуалізації, які звертаються до зон напряму |

Після зміни параметра стани іншого варіанта видаляються.

## Стани

| State | Опис |
| --- | --- |
| `info.connection` | Підключення до шлюзу |
| `info.ip` | Використовувана IP-адреса шлюзу |
| `light.on` | Увімк. / вимк. |
| `light.mode` | `white`, `colour` або `scene` — запис перемикає режим (кольоровий режим з останнім відтінком, режим сцени з останньою сценою) |
| `light.brightness` | Яскравість 1–100 % поточного режиму. 0 вимикає, значення більше 0 вмикає |
| `light.colorTemperature` | Колірна температура 2700–6500 K з кроком 100 K (перемикає в білий режим) |
| `light.color` | Колір у форматі `#rrggbb` за повної яскравості (перемикає в кольоровий режим). Запис задає відтінок і насиченість, яскравість значення RGB ігнорується — використовуйте `light.brightness` |
| `light.hue` | Відтінок 0–360° (перемикає в кольоровий режим) |
| `light.saturation` | Насиченість 0–100 % (перемикає в кольоровий режим) |
| `light.scene` | Сцена 1–9 (M1–M9 у застосунку), 0 = без сцени. Запис 1–9 запускає сцену |
| `light.speedUp` / `light.speedDown` | Кнопки S+ / S- застосунку: сцена швидше / повільніше. Шлюз не повідомляє швидкість |
| `light.countdown` | Секунди до перемикання ламп шлюзом (0 = вимк., стандартна точка даних 26) |
| `light.zone` | Лише під час вибору зони: зона команд `light.*`, 0 = усі зони, 1–8 |
| `zones.zone<n>.*` | Лише з окремим каналом для кожної зони: `on`, `mode`, `brightness`, `colorTemperature`, `color`, `hue`, `saturation`, `scene`, `speedUp`, `speedDown` для зони n |
| `dp101.raw` | Останній кадр точки даних 101 у Base64 — запис надсилає значення без змін |
| `dp101.hex` | Останній кадр точки даних 101 у шістнадцяткових байтах — запис надсилає кадр, контрольна сума додається або виправляється автоматично |
| `dp101.checksumValid` | Контрольна сума останнього кадру правильна |
| `dp101.history` | JSON-список останніх 50 кадрів (`rx` = отримано, `tx` = надіслано) з позначкою часу; повторювані однакові відповіді про стан не додаються |
| `raw.dp<n>` | Будь-яка інша точка даних, про яку повідомляє шлюз, створюється автоматично (доступна для запису) |

Значення, яким потрібен певний режим або увімкнені лампи, адаптер надсилає так само, як застосунок MiBoxer: наприклад, колірна температура в кольоровому режимі спочатку перемикає в білий режим, а яскравість за вимкнених ламп спочатку їх вмикає. Швидкі зміни (наприклад, з повзунка) об'єднуються, надсилається лише останнє значення. Команди приймаються лише за підключеного шлюзу. Команда вважається виконаною, коли наступний стан шлюзу показує її значення (приблизно через 2,5 с); до того стан не підтверджено.

## Точка даних 101 — протокол

WL-433 передає лампи, зони та сцени в специфічній для виробника точці даних 101: 12-байтові кадри в кодуванні Base64, останній байт — 8-бітна сума байтів 0–10. Формат розшифровано 22.09.2026 за кадрами стану реального шлюзу та командами, які застосунок MiBoxer записує у свій журнал Android:

| Кадр | Bytes (hex) | Значення |
| --- | --- | --- |
| Команда (застосунок / адаптер → шлюз) | `41 00 00 0B cc vv vv vv vv zz 80 ss` | `cc` команда: `01` відтінок 0–255 (значення в байтах 5–8, перемикає в кольоровий режим), `02` яскравість 1–100 %, `03` колірна температура 0–38 (2700 K + 100 K за крок), `04` насиченість 0–100 %, `05` сцена 1–9, `06` клавіша (`01` увімк., `02` вимк., `03` S-, `04` S+, `06` білий режим); `zz` зона: `00` усі, `01`–`08` |
| Запит стану | `43 00 00 80 00 00 00 00 00 80 80 C3` | шлюз відповідає кадром стану `44` |
| Стан (шлюз → застосунок) | `42` / `44` `00 00 00 mm hh tt bb ss 0B 01 xx` | `42` повідомлення про зміну (приблизно через 2,5 с після останньої зміни), `44` відповідь на запит; `mm` режим: `00` вимк., `01` колір, `02` білий, `03`–`0B` сцена 1–9; `hh` відтінок, `tt` крок колірної температури, `bb` яскравість, `ss` насиченість (0 у білому режимі). Зона не входить до стану |

Стандартні точки даних 20–23 шлюз виводить із цих команд; адаптер використовує лише точку даних 20 (увімк./вимк., надходить раніше за стан), а в усьому іншому дотримується стану з точки даних 101. Запис точки даних кольору Tuya 24 не змінює колір ламп — застосунок MiBoxer її теж не використовує.

Прямий доступ для власних експериментів: `dp101.hex` приймає 11 байтів (контрольна сума додається), наприклад `43 00 00 80 00 00 00 00 00 80 80` запитує стан.

## Обмеження

- Шлюз повідомляє один стан для всіх ламп (останнє налаштування), а не стан кожної зони — див. [Зони](#зони).
- Швидкість сцени (S+ / S-) шлюз не повідомляє.
- Неможливо побачити, чи лампа справді отримала команду радіоканалом: стан надходить від шлюзу.
- Шлюз і далі повідомляє свій стан у хмару Tuya. Повне блокування доступу до інтернету може зробити його ненадійним.

## Журналювання та пошук несправностей

Адаптер веде журнал за фіксованою схемою, щоб журнал у будь-який момент був корисним для пошуку помилок:

| Рівень | Що записується |
| --- | --- |
| error | Помилки конфігурації, через які адаптер не може працювати (немає ID пристрою, локальний ключ не з 16 символів) |
| warn | Проблеми, що потребують ваших дій, — повідомляються один раз, а потім лише на рівні debug, доки їх не усунуто: шлюз відхиляє підключення, дані неможливо розшифрувати (неправильний локальний ключ), команди не підтверджені шлюзом, запити стану без відповіді, неочікувані значення точок даних або кадри стану |
| info | Ключові події: зведення конфігурації під час запуску, шлюз знайдено, підключено, підключення втрачено, підключення знову стабільне, стани іншого варіанта зон видалено |
| debug | Кожен крок із вхідними даними, рішеннями та тривалістю: зміна стану → перетворення на кадри точки даних 101 (з причиною додаткових кадрів, наприклад «спочатку увімкнути») → черга → надсилання → підтвердження станом (або якого значення ще бракує), кожна отримана точка даних і стан та оновлені стани, запити стану, пошук. Команди (`#12`) і спроби підключення (`Attempt #3`) пронумеровано |
| silly | Додатково трасування протоколу бібліотеки tuyapi (пакети, ping/pong) з міткою `[tuyapi]` |

Кожне повідомлення починається з мітки: `[cfg]` конфігурація, `[conn]` підключення, `[rx]` шлюз → стани, `[cmd]` стани → команди, `[queue]` черга команд, `[poll]` оновлення та запит стану, `[disc]` пошук, `[dp101]` необроблені кадри, `[unload]` завершення, `[tuyapi]` трасування бібліотеки. Локальний ключ і ключі сеансу ніколи не з'являються в журналі — зведення конфігурації показує лише довжину ключа.

Зміна рівня: Admin → **Екземпляри** → режим експерта → рівень журналу `miboxer-wl433.0` → `debug` (або `silly` для трасування протоколу; потім перезапустіть екземпляр). Додавайте журнал debug і вміст `dp101.history`, коли повідомляєте про проблему.
